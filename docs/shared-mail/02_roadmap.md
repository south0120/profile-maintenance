# 共有メール管理システム 開発ロードマップと工数

> [00_decision.md](00_decision.md) / [01_architecture.md](01_architecture.md) の続き。自作する場合の段階と見積もり。
>
> 前提: 開発者1名、AI支援あり、TypeScript/React に習熟済み

---

## 1. 全体像

```
 PoC ──▶ 判断 ──▶ MVP ──▶ 実運用
2〜3人日        10〜15人日   +10〜20人日
   │
   └─ ここで「自作を続けるか / SaaSに切り替えるか」を決める
```

**最大の設計判断は「PoCで止められること」。** 全体を作り切ってから破綻に気づくのが最悪なので、最も不確実な部分（日本語の文字化けと同期の安定性）を最初の3人日に前倒しする。

---

## 2. PoC（2〜3人日）— 自作可否を判定する

### 目的

作ることではなく、**次の2つを実データで確認すること**。

1. 実際の業務メールが文字化けせずに読めるか（ISO-2022-JP / 件名 / 添付ファイル名）
2. 数日回して取りこぼし・重複が起きないか

### スコープ

| 入れる | 入れない |
|---|---|
| IMAP 1アドレスのみ | Gmail API 対応 |
| 受信一覧・本文表示 | 全文検索 |
| 担当者の割当 | テンプレート・社内コメント |
| ステータス変更（4値） | 権限管理・監査ログ |
| 返信（SMTP送信） | 添付の送信、誤送信防止 |
| ローカルPostgreSQL | 本番ホスティング |

### 内訳

| 作業 | 目安 |
|---|---|
| プロジェクト初期化（Next.js / DB / スキーマ） | 0.5人日 |
| ImapAdapter（差分取得＋UIDVALIDITY管理＋パース） | 1人日 |
| 画面（一覧・詳細・割当・ステータス・返信） | 1人日 |
| 実メールでの検証・文字化け対処 | 0.5人日 |

### 通過条件（Doneの定義）

- [ ] 実際の受信メール50通以上を取り込み、**文字化けが1通も無い**
- [ ] 3日間ワーカーを回して、取りこぼし・重複が0件
- [ ] 返信が相手に正しく届き、**同じスレッドにぶら下がる**（In-Reply-To が効いている）
- [ ] 2人で同時に触って、担当者・ステータスが破綻しない

**1つでも落ちたら、原因を1日で潰せるか判断する。潰せないならメールワイズ導入に切り替える。**

## 3. MVP（10〜15人日）— 実務で使える状態

### スコープ

| 機能 | 目安 |
|---|---|
| Gmail API 対応（GmailAdapter・OAuth・Internalアプリ設定） | 2〜3人日 |
| 複数メールボックス対応（3アドレス） | 1人日 |
| 二重対応の防止（可視化・下書き排他・楽観ロック） | 2人日 |
| 誤送信の防止（送信予約・宛先確認・社外警告） | 1人日 |
| 返信テンプレート | 0.5人日 |
| 社内コメント | 0.5人日 |
| 添付ファイル（受信保存・送信添付・R2連携） | 1.5人日 |
| 全文検索（PGroonga導入・検索UI） | 1人日 |
| 認証（Auth.js / Google・ドメイン限定） | 1人日 |
| デプロイ（VPS構築・ワーカー常駐化・バックアップ） | 1.5人日 |

### Doneの定義

- [ ] 3アドレス（Gmail・IMAP混在）を1画面で扱える
- [ ] 5人が同時に使って二重返信が起きない
- [ ] 送信予約の取り消しが動く
- [ ] 日本語で全文検索が引ける
- [ ] ワーカーが落ちたら画面で気づける（最終同期時刻の表示）

---

## 4. 実運用（+10〜20人日）— 任せられる状態

| 機能 | 目安 |
|---|---|
| 権限管理（ロール・メールボックス単位のアクセス制御） | 2人日 |
| 監査ログ | 1人日 |
| 顧客情報・対応履歴（contacts と過去やり取りの紐付け） | 2人日 |
| 集計（対応件数・初回返信までの時間） | 2人日 |
| 障害時の再取り込み・手動再同期の導線 | 2人日 |
| 日本語エンコーディングの作り込み（実運用で出た事例への対応） | 2〜4人日 |
| AI機能（自動下書き・要約・優先度判定） | 3〜5人日 |
| モバイル対応（レスポンシブ） | 1〜2人日 |

**AI機能はここに置いている**が、[00_decision.md](00_decision.md) §3 で「AI活用の自由度」が自作の主要な動機になっている場合は、MVP に前倒しして早めに価値を確かめたほうがよい。

---

## 5. 工数まとめ

| 段階 | 工数 | 累計 |
|---|---|---|
| PoC | 2〜3人日 | 3人日 |
| MVP | 10〜15人日 | 18人日 |
| 実運用 | +10〜20人日 | **28〜38人日（1〜1.5人月）** |

ランニング費用は VPS 約1,000〜2,000円/月 ＋ AI API 従量。年額で概ね 24,000〜36,000円。

参考: メールワイズは 5人で **約36,000円/年**。ランニングだけ見れば拮抗するが、**初期の1〜1.5人月が丸ごと上乗せ**になる。

---

## 6. 見直しのタイミング

| タイミング | 判断すること |
|---|---|
| PoC完了時 | 文字化け・同期が通ったか。**通らなければ即撤退** |
| MVP完了時 | 実務で1か月回してみて、SaaSに戻したくならないか |
| 利用者が10人を超えたら | 権限設計とパフォーマンスを再設計するか、SaaSに移すか |
| 他社提供を検討する段階 | マルチテナント化は作り直しに近い。ここは最初から狙うなら設計を変える |

---

## 7. 次のアクション

1. [00_decision.md](00_decision.md) §3 のチェックリストで、自作の動機が1つ以上あるか確認する
2. 動機がある → **PoC（2〜3人日）を別リポジトリで開始する**
3. 動機がない → メールワイズ スタンダード（5人・約36,000円/年）を導入する
